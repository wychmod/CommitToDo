# CommitToDo 产品定位

**版本**: 3.0.2
**更新日期**: 2026-11-20
**状态**: 方向已定，主用户已锁定，对象模型已收敛为单根分支树，待 MVP 验证
**作用域**: 全仓库

本文只回答三件事：**CommitToDo 是什么、为谁做、守什么底线**。

对象定义、信息架构、功能清单、徽章体系、版本切分一律以 [`FRAMEWORK.md`](./FRAMEWORK.md) 为唯一出处；技术落地待新工程规范定稿后重写（旧架构文档已归档至 `docs/archive/2026-11/legacy-impl/ARCHITECTURE.md`，不得引用）；视觉规范待重新设计，旧版已整体归档至 `docs/archive/2026-11/visual-system/`（不得引用）。**本文不复述它们的内容，避免两处维护。**

## 1. 一句话

**把「事情做完了」变成「看得见的路」。**

待办完成即留下一条提交。提交当天可纠错，跨天锁定。提交按真实时间与分支归属连起来，就是一棵可回看、可分叉、可汇合的分支树。

对外传播语：

- 情感版：**把答应自己的事，一件件兑现。**
- 结构版：**人生有主线，也允许支线。**

## 2. 命名决策

| 候选 | 判断 | 理由 |
|---|---|---|
| **`CommitToDo`** | **采用（2026-11-15 拍板）** | 用户决策：仓库名、PWA 安装名、页面标题、界面品牌统一用它；代码与既有文档已全部如此，零迁移成本。代价见下方「已知取舍」 |
| `人生小事` | 不作为主品牌 | 公开渠道已有同名 App（TinyTrove，本地加密时间线日记）；「小事」描述单位而非结构 |
| `人生主线` | 不作为主品牌 | 公开渠道已有同名 App（2026 年多个下载站收录 v1.1 / v1.2，定位为目标拆解 + 打卡 + 周报）；语义高度重叠 |
| `Commit` | 降为文档与代码内的简称 | 更短、更可英文传播；但产品名称已定 `CommitToDo`，`Commit` 不再单独作为对外品牌 |

决策：

- **产品名与一切用户可见名称：`CommitToDo`**。包括仓库名、PWA 安装名（`manifest.name` / `short_name`）、页面标题与描述、落地页品牌、登录页品牌、工作台顶栏、应用商店副标。**不得在不同位置混用两个名字。**
- `Commit` 仅作**文档正文与代码标识符的简称**（如「Commit 的护城河」「`commit_web`」「Commit Blue」）。文档标题统一写 `CommitToDo`。
- 应用商店副标：`CommitToDo · 人生提交记录`。
- `人生小事` 可保留为内容栏目名（如「本周人生小事」），不做产品名。

**已知取舍**（记录下来，避免以后反复讨论）：

`ToDo` 把品类写死在「待办工具」上，对外讲「人生主线」时名字会拖后腿；`Commit` 的双关（程序员读「提交」、普通人读「承诺」）本来能兼顾两个人群。选择 `CommitToDo` 换来的是**名字直白、与既有代码和用户认知一致、不用改任何实现**，代价是**传播叙事变弱**。这个代价接受，后续不再重开这个话题。

> 公开渠道信息检索于 2026-11-13，仅证明其他候选名不干净，不代表商标注册状态。正式启用前仍须做商标检索与法务确认；本文不构成法律意见。

## 3. 目标用户与人群策略

> **已定决策（2026-11-13）：主用户 = 程序员 / 技术型知识工作者。**
> 大众用户不作为首发对象，只作为**叙事对象**（讲故事的受众）与 V1 之后的扩散目标。
> 这条决策是排期与取舍的唯一裁判：MVP 阶段任何「为降低门槛而牺牲结构」的改动，都不做。

### 3.1 主用户：程序员 / 技术型知识工作者

MVP 与 V1 的**唯一验收对象**。

- 已经在用 Git 思维：分支、合并、回滚不需要解释，对「同时推进多条线」有天然直觉。
- 能忍受结构化输入（建领域、开项目、写一句话），愿意为「图谱 / 可追溯」买单。
- 是当前 Web 版本的现成用户，也是最好的共创者——能给出可执行的产品反馈，而不是「挺好用」。
- 关键判断：这群人**已经被 Git 教育过一次**，我们不需要支付教育成本；这是本项目唯一的结构性优势。

### 3.2 扩散用户：25–35 岁城市知识工作者

V1 之后才进入验收范围，MVP 不为他们做妥协。

- 正在做年度规划、周复盘、人生节点记录的人。
- 不关心 Git，只关心「我有没有在推进真正重要的事」。
- 获取渠道：即刻、小红书、播客、工具类内容社区。

### 3.3 策略

- **主用户先跑通闭环，扩散人群只负责听故事**。MVP 发布渠道是技术社区（V2EX、GitHub、掘金、少数派），不是小红书。
- 对外只讲一个故事：人生主线；不讲「给人生做版本控制」。
- **全产品只有一套结构语言：分支 / 待办 / 提交**。不设项目模式与人生模式两套词表；「历程」是同一棵树的时间渲染，只改时间尺度，不改用词。

### 3.4 这条决策改变了什么

| 议题 | 若主用户是大众 | 主用户是程序员（已选） |
|---|---|---|
| 首次进入 | 必须 Onboarding 引导，否则流失 | 可以先给一棵示例树 + 一句口头比喻，引导可后置 |
| 界面用语 | 默认「分支 / 待办 / 提交」，全产品只有一套词 | 同一套词，不出现英文标识符 |
| 输入成本 | 每多一个字段都是流失点 | 「一句话记录」是习惯，不是负担 |
| 数据可信度 | 需要云端同步才敢用 | 本地优先，支持导出与恢复（同步延到 V2） |
| 分享 | 分享是核心增长 | 分享是加分项，图谱截图即可 |
| 最大风险 | 学不会 | 觉得「这不就是 git 吗」，缺乏新鲜感 |

最后一行是这个决策真正的代价：**程序员会立刻理解，也会立刻厌倦**。所以差异化不能停在「git 化的 todo」，必须落在「提交当天可纠错、跨天锁定」「停滞虚线」「徽章长在树上」这三件事上（见 `FRAMEWORK.md` §6.1）。

## 5. 两条硬约束

这两条是产品级红线，跨越所有功能与所有版本，写在定位文档而不是框架文档里，因为它们不随功能调整而变。

### 5.1 界面铁律：借结构，不借元数据

用户看到的是「分支 / 待办 / 提交」，不是 Git。**机制可以像 Git，界面不能是 Git。**

禁止出现在界面正文：

- `a3f9c1` 之类的提交哈希
- `feature/guitar` 之类的分支路径
- `feat(auth): ...` 之类的规范式提交前缀
- `merge commit`、`HEAD`、`ref`、`origin`、`DAG` 等裸术语
- 任何以英文标识符作为主标题的列表项

允许出现的英文：品牌名 `CommitToDo`、用户自己输入的内容、§5.2 注解里的括号补充。

界面上一个节点应该是 **「第一次半马 · 2025 年 4 月 6 日」**，而不是 `a3f9c1 (HEAD -> main) feat: first half marathon`。

> 这条不是审美偏好，是产品定位的直接推论：主用户是程序员，他有真 Git；他要的是把这些年零散的工作、副业、健身、读书放进同一棵树，不是再看一遍 git log。

**只有一种视角**：全产品统一用「分支 / 待办 / 提交 / 里程碑 / 徽章」，不设第二套词表。「历程」是同一棵树按时间尺度重画，只改密度与聚合，不改用词、不改数据归属。

### 5.2 知识注解：在用的地方解释，不在说明书里解释

「让人顺便懂点计算机」不靠术语表，靠**在具体动作旁边一句人话**。用户不必先学，想知道时随时能懂。

| 触发点 | 注解文案（一句话，默认折叠） |
|---|---|
| 第一次进分支树 | 每条线就是你正在推的一件事，可以同时有好几条。 |
| 图上出现两条线 | 你在同时推进两件事，所以线分开了；做完会并回父分支，过程不会丢。 |
| 里程碑节点 | 里程碑是你亲手插的锚点，不是系统算出来的，所以它比普通提交更醒目。 |
| 停滞虚线 | 这条线 97 天没有新提交，我们把它画成虚线——很多工具不会提醒你这件。 |

**四个概念的口径与正式文案以 [`FRAMEWORK.md`](./FRAMEWORK.md) §4.9 I-01 为唯一出处**（分支是什么 / 合并是什么意思 / 里程碑与提交的区别 / 停滞虚线为什么是虚线）。本表只示范触发位置与语气，不另行定义概念。

规则：

- 默认只显示一次，一句话说完；不弹窗、不打断、不写第二段。
- 用户可全局关闭。
- 单条文案不得出现超过一个 Git 术语，且术语后必须紧跟一句白话解释。
- 不做「Git 小课堂」专题页——那会变成需要长期维护的教程，且没人看。

## 6. 产品原则

1. **说人话**：界面上不出现英文标识符，所有条目都是用户自己能读懂的中文句子（§5.1）。
2. **记录成本小于 3 秒**：完成后一句话即可，可留空；强制反思会杀死留存。
3. **图在 10 个节点时就要有意义**：先回填主干，再长叶子。
4. **一个动作，多个视图**：不新增需要单独维护的「分支树」模块；树是渲染层，不是模块。
5. **本地优先是信任基础**：人生数据不上云也能用；同步是增值，不是前提。
6. **不做人生导师**：只呈现事实与问题，不给人生建议。
7. **每个视图必须回答一个问题**：回答不了就砍掉。
8. **好看是功能，不是装饰**：留白、对齐、字号层级决定用户敢不敢每天打开；「能用但难看」等于不能用。

## 7. 不做什么

跨版本的永久边界。功能级的「建议不做」见 `FRAMEWORK.md` §6.3，此处只留定位级红线。

- 团队协作 / 甘特图 / 多成员项目
- 笔记 / 知识库 / 第二大脑
- 社交 feed / 排行榜 / 打卡竞赛
- 复杂自定义字段 / 多维表格
- 日历双向同步（先做单向展示）
- 强制日记 / 强制反思
- 独立的人生版 App / 两套数据结构 —— 全产品只有一棵分支树、一套词
- 暴露 Git 元数据的开发者视图（哈希、分支路径、diff）—— 要看去真 Git，这里只呈现人能读懂的东西

## 8. 关键风险

| 风险 | 概率 | 影响 | 应对 |
|---|---|---|---|
| 记录成本高，用户不愿写说明 | 高 | 高 | 一句话可留空、快速添加、周回顾代偿 |
| 冷启动图空白，看不出意义 | 高 | 中 | 示例树、回填、模板 |
| 双人群定位撕裂 | 中 | 高 | 一套引擎一套词表；对外只讲一个叙事 |
| 数据丢失 / 无同步 | 中 | 极高 | 自动备份、导出与恢复、V2 加密同步 |
| 产品膨胀成「人生 OS」 | 高 | 中 | 不做清单；每个视图必须回答问题 |
| 命名侵权 | 未知 | 高 | 商标检索、备选名 |
| 图示虚荣，好看但无决策价值 | 中 | 中 | 每个视图绑定一个具体问题与验收 |

## 9. 待验证假设

| 编号 | 假设 | 验证方式 | 通过阈值（建议，待校准） |
|---|---|---|---|
| H1 | 用户愿意在完成时补一句话 | 埋点：带自定义内容的提交占比 | ≥30% |
| H2 | 回填能提升首周留存 | A/B：有回填引导 vs 无回填 | D7 留存 +10pp |
| H3 | 用户能读懂分支树 | 5 人可用性测试 | ≥4 人能说出自己的一级分支 |
| H4 | 分享图能带来回流 | 分享链接带来源参数 | 分享率 ≥5%，回流 ≥1% |
| H5 | 分支树能让程序员在没有人生叙事需求时也留下来 | 观察：MVP 种子中「历程」的打开率与次月留存 | 历程周活 ≥30%，且不显著低于「今天」 |

> 以上为待验证假设，不是已验证结论；对外表述不得当作事实使用。
