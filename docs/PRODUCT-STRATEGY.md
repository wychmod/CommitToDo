# Commit 产品定位

**版本**: 2.0.0
**更新日期**: 2026-11-15
**状态**: 方向已定，主用户已锁定，待 MVP 验证
**作用域**: 全仓库

本文只回答三件事：**Commit 是什么、为谁做、守什么底线**。

对象定义、信息架构、功能清单、徽章体系、版本切分一律以 [`FRAMEWORK.md`](./FRAMEWORK.md) 为唯一出处；技术落地见 [`ARCHITECTURE.md`](./ARCHITECTURE.md)；视觉规范见 [`DESIGN.md`](./DESIGN.md)。**本文不复述它们的内容，避免两处维护。**

---

## 1. 一句话

**把「事情做完了」变成「看得见的路」。**

任务完成即留下一条不可改动的记录，记录按真实时间与归属关系连起来，就是一条可回看、可分叉、可汇合的人生历程。

对外传播语：

- 情感版：**把答应自己的事，一件件兑现。**
- 结构版：**人生有主线，也允许支线。**

## 2. 命名决策

| 候选 | 判断 | 理由 |
|---|---|---|
| `CommitToDo` | 不作为用户可见主品牌 | `ToDo` 把品类写死为待办工具，无法承载人生主线；保留为内部代号与仓库名 |
| `人生小事` | 不作为主品牌 | 公开渠道已有同名 App（TinyTrove，本地加密时间线日记）；「小事」描述单位而非结构 |
| `人生主线` | 不作为主品牌 | 公开渠道已有同名 App（2026 年多个下载站收录 v1.1 / v1.2，定位为目标拆解 + 打卡 + 周报）；语义高度重叠 |
| **`Commit`** | **采用** | 双关：程序员读「提交」，普通人读「承诺」；短、可英文传播、不排斥大众 |

决策：

- 品牌名：`Commit`；不再使用 `CommitToDo` 作为用户可见名称。
- 应用商店副标：`Commit · 人生提交记录`。
- 正式启用前必须做商标检索与法务确认；本文不构成法律意见。
- `人生小事` 可保留为内容栏目名（如「本周人生小事」），不做产品名。

> 公开渠道信息检索于 2026-11-13，仅证明名称不干净，不代表商标注册状态。

## 3. 目标用户与人群策略

> **已定决策（2026-11-13）：主用户 = 程序员 / 技术型知识工作者。**
> 大众用户不作为首发对象，只作为**叙事对象**（讲故事的受众）与 V1 之后的扩散目标。
> 这条决策是排期与取舍的唯一裁判：MVP 阶段任何「为降低门槛而牺牲结构」的改动，都不做。

### 3.1 主用户：程序员 / 技术型知识工作者

MVP 与 V1 的**唯一验收对象**。

- 已经在用 Git 思维：分支、合并、回滚不需要解释，对「同时推进多条线」有天然直觉。
- 能忍受结构化输入（建领域、开项目、写一句话），愿意为「图谱 / 可追溯」买单。
- 是当前 Web 版本的现成用户，也是最好的共创者——能给出可执行的产品反馈，而不是「挺好用」。
- 关键判断：这群人**已经被 Git 教育过一次**，我们不需要支付教育成本；这是本项目唯一的结构性优势。

### 3.2 扩散用户：25–35 岁城市知识工作者

V1 之后才进入验收范围，MVP 不为他们做妥协。

- 正在做年度规划、周复盘、人生节点记录的人。
- 不关心 Git，只关心「我有没有在推进真正重要的事」。
- 获取渠道：即刻、小红书、播客、工具类内容社区。

### 3.3 策略

- **主用户先跑通闭环，扩散人群只负责听故事**。MVP 发布渠道是技术社区（V2EX、GitHub、掘金、少数派），不是小红书。
- 对外只讲一个故事：人生主线；不讲「给人生做版本控制」。
- **项目模式是主用户的默认值**，人生模式是同一个应用的另一套视角，不是「新手版」。两者都说中文，差别在管交付还是管历程（§5.1）。

### 3.4 这条决策改变了什么

| 议题 | 若主用户是大众 | 主用户是程序员（已选） |
|---|---|---|
| 首次进入 | 必须 Onboarding 引导，否则流失 | 可以先给一棵示例树 + 一句口头比喻，引导可后置 |
| 界面用语 | 默认「领域 / 主线 / 小事」 | 默认「项目 / 并行线 / 待办」，可一键切换；两者都不出现英文标识符 |
| 输入成本 | 每多一个字段都是流失点 | 「一句话记录」是习惯，不是负担 |
| 数据可信度 | 需要云端同步才敢用 | 本地优先 + 可导出即够（同步延到 V2） |
| 分享 | 分享是核心增长 | 分享是加分项，图谱截图即可 |
| 最大风险 | 学不会 | 觉得「这不就是 git 吗」，缺乏新鲜感 |

最后一行是这个决策真正的代价：**程序员会立刻理解，也会立刻厌倦**。所以差异化不能停在「git 化的 todo」，必须落在「记录不可改 + 停滞虚线 + 徽章长在树上」这三件 Git 本身没有的东西上（见 `FRAMEWORK.md` §6.1）。

## 5. 两条硬约束

这两条是产品级红线，跨越所有功能与所有版本，写在定位文档而不是框架文档里，因为它们不随功能调整而变。

### 5.1 界面铁律：不出现英文标识符

产品内部用 Git 的机制承载历史，但 **Git 不是界面语言**。

禁止出现在界面正文：

- `a3f9c1` 之类的提交哈希
- `feature/guitar` 之类的分支名
- `feat(auth): ...` 之类的规范式提交前缀
- `merge commit`、`HEAD`、`ref`、`origin`、`DAG` 等裸术语
- 任何以英文标识符作为主标题的列表项

允许出现的英文：品牌名 `Commit`、用户自己输入的内容、§5.2 注解里的括号补充。

界面上一个节点应该是 **「第一次半马 · 2025 年 4 月 6 日」**，而不是 `a3f9c1 (HEAD -> main) feat: first half marathon`。

> 这条不是审美偏好，是产品定位的直接推论：主用户是程序员，他有真 Git；他要的是把这些年零散的项目、副业、健身、读书放进同一张图，不是再看一遍 git log。

**两种模式的分工**（显示名见 `FRAMEWORK.md` §2）：

| | 项目模式（默认） | 人生模式 |
|---|---|---|
| 组织方式 | 项目 → 并行线 → 待办 | 人生领域 → 主线 → 小事 |
| 一条记录长什么样 | 「修好 Safari 下登录页崩溃」 | 「第一次跑完 10 公里」 |
| 主视图 | 项目进度 + 并行线关系 | 人生树 + 领域分布 |
| 回答的问题 | 这个项目推到哪了，卡在哪 | 我这一年活成了什么样 |
| 时间尺度 | 天 / 周 / 迭代 | 月 / 年 |

模式改变的是**视角与分组**，不是语言，也不是数据归属。两者共用同一套组件、同一批数据；任何需要写两遍的界面，都说明设计错了。

### 5.2 知识注解：在用的地方解释，不在说明书里解释

「让人顺便懂点计算机」不靠术语表，靠**在具体动作旁边一句人话**。用户不必先学，想知道时随时能懂。

| 触发点 | 注解文案（一句话，默认折叠） |
|---|---|
| 完成记录后 | 完成会留下一条不可改动的记录，写错了只能追加更正——所以回看时才可信。 |
| 图上出现两条线 | 你在同时推进两件事，所以线分开了；做完会汇回主线，过程不会丢。 |
| 里程碑节点 | 里程碑是你亲手插的锚点，不是系统算出来的，所以它比普通记录更醒目。 |
| 停滞虚线 | 这条线 97 天没有新记录，我们把它画成虚线——很多工具不会提醒你这件。 |

规则：

- 默认开启，一句话说完；不弹窗、不打断、不写第二段。
- 用户可全局关闭。
- 单条文案不得出现超过一个 Git 术语，且术语后必须紧跟一句白话解释。
- 不做「Git 小课堂」专题页——那会变成需要长期维护的教程，且没人看。

## 6. 产品原则

1. **说人话**：界面上不出现英文标识符，所有条目都是用户自己能读懂的中文句子（§5.1）。
2. **记录成本小于 3 秒**：完成后一句话即可，可留空；强制反思会杀死留存。
3. **图在 10 个节点时就要有意义**：先回填主干，再长叶子。
4. **一个动作，多个视图**：不新增需要单独维护的「人生树」模块；人生树是渲染层，不是模块。
5. **本地优先是信任基础**：人生数据不上云也能用；同步是增值，不是前提。
6. **不做人生导师**：只呈现事实与问题，不给人生建议。
7. **每个视图必须回答一个问题**：回答不了就砍掉。
8. **好看是功能，不是装饰**：留白、对齐、字号层级决定用户敢不敢每天打开；「能用但难看」等于不能用。

## 7. 不做什么

跨版本的永久边界。功能级的「建议不做」见 `FRAMEWORK.md` §6.3，此处只留定位级红线。

- 团队协作 / 甘特图 / 多成员项目
- 笔记 / 知识库 / 第二大脑
- 社交 feed / 排行榜 / 打卡竞赛
- 复杂自定义字段 / 多维表格
- 日历双向同步（先做单向展示）
- 强制日记 / 强制反思
- 独立的人生版 App / 两套数据模型 —— 模式是同一个应用的两套读法，不是两个产品
- 暴露 Git 元数据的开发者视图（哈希、分支名、diff）—— 要看去真 Git，这里只呈现人能读懂的东西

## 8. 关键风险

| 风险 | 概率 | 影响 | 应对 |
|---|---|---|---|
| 记录成本高，用户不愿写说明 | 高 | 高 | 一句话可留空、快速添加、周回顾代偿 |
| 冷启动图空白，看不出意义 | 高 | 中 | 示例树、回填、模板 |
| 双人群定位撕裂 | 中 | 高 | 一套引擎两种视角；对外只讲一个叙事 |
| 数据丢失 / 无同步 | 中 | 极高 | 自动备份、导出、V2 加密同步 |
| 产品膨胀成「人生 OS」 | 高 | 中 | 不做清单；每个视图必须回答问题 |
| 命名侵权 | 未知 | 高 | 商标检索、备选名 |
| 图示虚荣，好看但无决策价值 | 中 | 中 | 每个视图绑定一个具体问题与验收 |

## 9. 待验证假设

| 编号 | 假设 | 验证方式 | 通过阈值（建议，待校准） |
|---|---|---|---|
| H1 | 用户愿意在完成时补一句话 | 埋点：带自定义内容的记录占比 | ≥30% |
| H2 | 回填能提升首周留存 | A/B：有回填引导 vs 无回填 | D7 留存 +10pp |
| H3 | 用户能读懂人生树 | 5 人可用性测试 | ≥4 人能说出自己的主线 |
| H4 | 分享图能带来回流 | 分享链接带来源参数 | 分享率 ≥5%，回流 ≥1% |
| H5 | 人生树能让程序员在没有人生叙事需求时也留下来 | 观察：MVP 种子中人生模式的打开率与次月留存 | 人生模式周活 ≥30%，且不显著低于项目模式 |

> 以上为待验证假设，不是已验证结论；对外表述不得当作事实使用。
