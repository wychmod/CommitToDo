# Commit 产品定位与核心模型

**版本**: 1.3.0
**更新日期**: 2026-11-13
**状态**: 方向已定，主用户已锁定，待 MVP 验证
**作用域**: 全仓库

本文回答三个问题：Commit 是什么、为谁做、用什么模型承载。功能排期见 [`ROADMAP.md`](./ROADMAP.md)，功能细则见 [`PRD.md`](./PRD.md)，技术落地见 [`ARCHITECTURE.md`](./ARCHITECTURE.md)。

---

## 1. 一句话

**Commit 把人生当成一条主线，把每件小事变成一次提交。**

任务完成即提交，提交挂在主线上，主线归属人生领域；所有提交按时间连起来，就是一条可回看、可分叉、可合并的人生历程。

对外传播语：

- 情感版：**把答应自己的事，一件件兑现。**
- 结构版：**人生有主线，也允许支线。**

## 2. 命名决策

| 候选 | 判断 | 理由 |
|---|---|---|
| `CommitToDo` | 不作为用户可见主品牌 | `ToDo` 把品类写死为待办工具，无法承载人生主线；保留为内部代号与仓库名 |
| `人生小事` | 不作为主品牌 | 公开渠道已有同名 App（TinyTrove，本地加密时间线日记）；「小事」描述单位而非结构 |
| `人生主线` | 不作为主品牌 | 公开渠道已有同名 App（2026 年多个下载站收录 v1.1 / v1.2，定位为目标拆解 + 打卡 + 周报）；语义高度重叠 |
| **`Commit`** | **采用** | 双关：程序员读「提交」，普通人读「承诺」；短、可英文传播、不排斥大众 |

决策：

- 品牌名：`Commit`；不再使用 `CommitToDo` 作为用户可见名称。
- 应用商店副标：`Commit · 人生提交记录`。
- 正式启用前必须做商标检索与法务确认；本文不构成法律意见。
- `人生小事` 可保留为内容栏目名（如「本周人生小事」），不做产品名。

> 公开渠道信息检索于 2026-11-13，仅证明名称不干净，不代表商标注册状态。

## 3. 目标用户与人群策略

> **已定决策（2026-11-13）：主用户 = 程序员 / 技术型知识工作者。**
> 大众用户不作为首发对象，只作为**叙事对象**（讲故事的受众）与 V1 之后的扩散目标。
> 这条决策是排期与取舍的唯一裁判：MVP 阶段任何「为降低门槛而牺牲结构」的改动，都不做。

### 3.1 主用户：程序员 / 技术型知识工作者

MVP 与 V1 的**唯一验收对象**。

- 已经在用 Git 思维：分支、合并、回滚不需要解释，项目模式对他是零学习成本，而不是「能看懂 Git 界面」。
- 能忍受结构化输入（建领域、拆主线、写提交说明），愿意为「图谱 / 可追溯」买单。
- 是当前 Web 版本的现成用户，也是最好的共创者——能给出可执行的产品反馈，而不是「挺好用」。
- 关键判断：这群人**已经被 Git 教育过一次**，我们不需要支付教育成本；这是本项目唯一的结构性优势。

### 3.2 扩散用户：25–35 岁城市知识工作者

V1 之后才进入验收范围，MVP 不为他们做妥协。

- 正在做年度规划、周复盘、人生节点记录的人。
- 不关心 Git，只关心「我有没有在推进真正重要的事」。
- 获取渠道：即刻、小红书、播客、工具类内容社区。

### 3.3 策略

- **主用户先跑通闭环，扩散人群只负责听故事**。MVP 发布渠道是技术社区（V2EX、GitHub、掘金、少数派），不是小红书。
- 对外只讲一个故事：人生主线；不讲「给人生做版本控制」。
- **项目模式是主用户的默认值**，人生模式是同一个应用的另一套视角，不是「新手版」。两者都说中文，差别在管交付还是管历程。

### 3.4 这条决策改变了什么

| 议题 | 若主用户是大众 | 主用户是程序员（已选） |
|---|---|---|
| 首次进入 | 必须 Onboarding 引导，否则流失 | 可以先给一棵示例树 + 一句口头比喻「这就是你人生的提交记录」，M-07 可后置 |
| 界面用语 | 默认「领域 / 主线 / 支线 / 里程碑」 | 默认「项目 / 并行线 / 待办」，可一键切换（M-02）；两者都不出现英文标识符 |
| 输入成本 | 每多一个字段都是流失点 | 「记录说明」是习惯，不是负担 |
| 数据可信度 | 需要云端同步才敢用 | 本地优先 + 可导出即够（同步延到 V2） |
| 分享 | 分享是核心增长 | 分享是加分项，图谱截图即可 |
| 最大风险 | 学不会 | 觉得「这不就是 git 吗」，缺乏新鲜感 |

最后一行是这个决策真正的代价：**程序员会立刻理解，也会立刻厌倦**。所以差异化不能停在「git 化的 todo」，必须落在 §4 的**人生领域 + 里程碑 + 年度章节**上——那是 Git 本身没有的东西。

## 4. 核心模型

### 4.1 两个轴

| 轴 | 结构 | 回答的问题 |
|---|---|---|
| 归属轴（树） | 人生领域 → 主线 → 支线 → 任务 | 这件事属于我人生的哪一块 |
| 历程轴（图） | 记录 → 分叉 → 汇合 → 里程碑 | 我是怎么走到今天的 |

两个轴作用于同一个对象：一个任务既有归属（`branchId`），也有历程（提交序列）。不是两套数据，也不是两个模块。

### 4.2 实体

| 实体 | 产品名 | 说明 | 与现状映射 |
|---|---|---|---|
| `LifeArea` | 人生领域 | 健康 / 事业 / 关系 / 成长 / 财务，可增删改 | 新增 |
| `Repository` | 主线 | 长期方向，归属一个领域 | 现有仓库 |
| `Branch` | 支线 | 从主线分叉的并行尝试 | 现有分支 |
| `Task` | 任务 / 小事 | 可执行单元 | 现有任务 |
| `Commit` | 完成记录 / 足迹 | 任务状态变更的不可变记录 | 现有提交 |
| `Milestone` | 里程碑 | 人生经历锚点，可带备注与照片 | 新增 |

> 代码层保留 `Repository` / `Branch` 命名，产品层通过术语映射呈现为主线 / 支线，避免全仓重命名带来的迁移风险。`Branch` 中 `isMain=true` 为主线主干，其余为支线；映射规则见 §7。

### 4.3 不变量

1. 一条主线必须归属且只归属一个领域。
2. 一条支线必须归属一条主线；分叉关系记录 `parentBranchId`。
3. 一个任务必须归属一条分支（`main` 主干或支线）；任务完成必须产生一条提交。
4. 提交不可修改、不可删除；纠错通过新提交表达。
5. 里程碑是独立时间锚点，不参与完成率统计。
6. 完成率口径：`done ÷ (todo + inProgress + done)`，`cancelled`（放下）不计入分母，单独统计放下率。
7. 同一语义只有一种定义；界面文案可以换皮，计算口径不能换。

### 4.4 为什么不是三个模块

- Todo 是执行视图，Git 图是历程结构，人生树是归属结构。
- 三者共用一份数据，不需要三次录入。
- 任何新增能力先问：它改变的是任务、提交、主线还是领域？落不到实体上就不做。

### 4.5 树与图的边界

- Git 历史是 DAG，不是树；「人生树」是对外隐喻，底层按图建模。
- 树负责归属，图负责时间；不把「人生树」做成独立入口。
- 人生树是历程图的一种读法，不是第四份数据。

## 5. 三种视图

| 视图 | 回答的问题 | 使用频率 | 成功信号 |
|---|---|---|---|
| 今天 | 我现在做什么 | 每天 | 日活、完成任务数 |
| 主线（项目模式下叫「项目」） | 精力是否在正确的方向 | 每周 | 周复盘打开率、停滞主线发现数 |
| 历程（人生模式下叫「人生树」） | 我怎么走到这里 | 每月 / 每年 | 回看时长、分享率 |

原则：三个入口，一份数据；任何一次记录，三个视图同时更新。

**「历程」只有一套渲染**：真实时间轴 + 一句话节点 + 里程碑大节点 + 停滞虚线（§7.5）。两种模式共用，只是着色与分组不同——不做两套图。

---

## 6. 人生经历如何进入

1. **回填**：onboarding 可选 3–5 个过去节点（毕业 / 入职 / 搬家 / 结婚 / 开始健身）。
2. **里程碑**：随时记录，日期 + 标题 + 一句话 + 可选照片。
3. **年度章节**：按年聚合提交与里程碑，自动生成复盘页。
4. 不要求写日记；任务完成本身就是记录。

## 7. 两种视角，一种语言

> 本节经过三次修订。1.0「术语皮肤」只换词不换读法；1.1「工程模式」被错做成 Git 界面（显示 sha、branch ref）——那是个假想用户，真实场景里程序员写的也是「修好 Safari 下登录页崩溃」这种中文待办。1.2 定稿：**两种模式都必须说人话，Git 只是底层机制，不是界面语言。**

### 7.1 模式改变的是视角，不是语言

两种模式的共同点：中文、自然语句、以「我要做的事」为单位。

| | 项目模式（默认） | 人生模式 |
|---|---|---|
| 组织方式 | 项目 → 并行线 → 待办 | 人生领域 → 主线 → 小事 |
| 一条记录长什么样 | 「修好 Safari 下登录页崩溃」 | 「第一次跑完 10 公里」 |
| 主视图 | 项目进度 + 并行线关系 | 人生树 + 领域分布 |
| 回答的问题 | 这个项目推到哪了，卡在哪 | 我这一年活成了什么样 |
| 时间尺度 | 天 / 周 / 迭代 | 月 / 年 |
| 默认落地 | 今天（按项目分组） | 今天（按领域分组） |

一句话：**项目模式管「交付」，人生模式管「历程」。两者都不是「Git 客户端」。**

### 7.2 界面铁律：不出现英文标识符

这是硬约束，写进来是为了防止开发时下意识「把 git log 搬上来」。

禁止出现在界面正文：

- `a3f9c1` 之类的提交哈希
- `feature/guitar` 之类的分支名
- `feat(auth): ...` 之类的规范式提交前缀
- `merge commit`、`HEAD`、`ref`、`origin`、`DAG` 等裸术语
- 任何以英文标识符作为主标题的列表项

允许出现的英文：品牌名 `Commit`、用户自己输入的内容、§7.4 注解里的括号补充。

界面上一个节点应该是 **「第一次半马 · 2025 年 4 月 6 日」**，而不是 `a3f9c1 (HEAD -> main) feat: first half marathon`。

### 7.3 术语对照：Git 词退到注解里

| 同一件事 | 项目模式 | 人生模式 | 只有注解才会说 |
|---|---|---|---|
| 长期方向 | 项目 | 主线 | 仓库 repository |
| 并行推进 | 并行线 | 支线 | 分支 branch |
| 可执行单元 | 待办 | 小事 | — |
| 完成动作 | 完成记录 | 足迹 | 提交 commit |
| 汇回 | 合回主线 | 汇入主线 | 合并 merge |
| 结束 | 结项 | 放下 | 归档 archive |
| 锚点 | 里程碑 | 里程碑 / 章节 | 标签 tag |

第四列是**唯一**会出现 Git 词的地方，且只在用户主动点开时出现。

### 7.4 知识注解：在用的地方解释，不在说明书里解释

「让人顺便懂点计算机」不靠术语表，靠**在具体动作旁边一句人话**。这是 AI 时代该有的科普方式：用户不必先学，想知道时随时能懂。

| 触发点 | 注解文案（一句话，默认折叠） |
|---|---|
| 完成记录后 | 完成会留下一条不可改动的记录，写错了只能追加更正——所以回看时才可信。 |
| 图上出现两条线 | 你在同时推进两件事，所以线分开了；做完会合回主线，过程不会丢。 |
| 里程碑节点 | 里程碑是你亲手插的锚点，不是系统算出来的，所以它比普通记录更醒目。 |
| 停滞虚线 | 这条线 97 天没有新记录，我们把它画成虚线——很多工具不会提醒你这件。 |

规则：

- 默认开启，一句话说完；不弹窗、不打断、不写第二段。
- 用户可全局关闭。
- 单条文案不得出现超过一个 Git 术语，且术语后必须紧跟一句白话解释。
- 不做「Git 小课堂」专题页——那会变成需要长期维护的教程，且没人看。

### 7.5 人生树（内部称呼：人生 Git 树）

命名保留「人生 Git 树」：名字里的 Git 是**来源说明**，不是界面语言。界面上它就叫「人生树」，在项目模式下叫「历程」。

**定义**：同一批记录，按真实时间与归属关系画出的图。**只有一套渲染，不做两套图。**

渲染规则（全部零英文）：

1. **横轴是真实时间**，不是序号。间距按天 / 月缩放，「三个月没动」就是一大段空白。
2. **节点只有三样东西**：一句话、日期、所属主线的颜色。没有哈希、没有分支名、没有前缀。
3. **里程碑是加粗大节点**，可挂备注（V1 加照片），是图上唯一比普通记录「重」的东西。
4. **按年分区**：每年一条时间带，卷起来就是年度章节（V1）。
5. **分叉 / 汇合说人话**：「这条支线在 6 月并回了主线」，不写 merge。
6. **停滞段显式标注**：某条主线 30 天无记录，那段线变虚线并标「已停滞 97 天」。

第 6 条是这个视图真正的价值：**Git 不会告诉你一条分支三个月没动了，但人生树必须告诉你**。项目模式回答「项目推到哪了」，人生模式回答「我多久没碰这件事了」。

**为什么这对程序员成立**：他要的不是在待办软件里再看一遍 git log——他有真 git。他要的是把这些年零散的项目、副业、健身、读书放进同一张图，看见自己实际走的路。形状熟悉只降低理解成本，不是卖点。

### 7.6 规则

- 默认按 onboarding 选择；设置可随时切换。模式存本地配置（MVP 无账号也能用），登录后随账户同步。
- 切换只改分组与叙事，不改数据、不改路由、不改统计口径。
- 一个项目可以同时被标为人生主线：它在两个模式里都出现，但呈现方式不同（项目模式看进度，人生模式看历程）。**模式决定「默认看什么」，不决定「数据属于谁」。**
- 项目模式不是「高级模式」，人生模式也不是「新手模式」，不设功能门槛、不限制同时可见。
- 两种模式共用同一套组件，只在分组方式、文案表与渲染开关上分叉；**任何需要写两遍的界面，都说明设计错了**。

## 8. 产品原则

1. **说人话**：界面上不出现英文标识符，所有条目都是用户自己能读懂的中文句子（§7.2）。术语只在注解里出现。
2. **记录成本小于 3 秒**：完成后一句话即可，可留空；强制反思会杀死留存。
3. **图在 10 个节点时就要有意义**：先回填主干，再长叶子。
4. **一个动作，三个视图**：不新增需要单独维护的「人生树」模块；人生树是渲染层，不是模块。
5. **本地优先是信任基础**：人生数据不上云也能用；同步是增值，不是前提。
6. **不做人生导师**：只呈现事实与问题，不给人生建议。
7. **每个视图必须回答一个问题**：回答不了就砍掉。
8. **好看是功能，不是装饰**：留白、对齐、字号层级决定用户敢不敢每天打开；「能用但难看」等于不能用。

## 9. 不做什么

- 团队协作 / 甘特图 / 多成员项目
- 笔记 / 知识库 / 第二大脑
- 社交 feed / 排行榜 / 打卡竞赛
- 复杂自定义字段 / 多维表格
- 日历双向同步（先做单向展示）
- 强制日记 / 强制反思
- 独立的人生版 App / 两套数据模型 —— 模式是同一个应用的两套读法，不是两个产品
- 暴露 Git 元数据的开发者视图（哈希、分支名、diff）—— 要看去真 Git，这里只呈现人能读懂的东西

## 10. 关键风险

| 风险 | 概率 | 影响 | 应对 |
|---|---|---|---|
| 记录成本高，用户不愿写说明 | 高 | 高 | 自动消息、可选一句话、周复盘代偿 |
| 冷启动图空白，看不出意义 | 高 | 中 | 回填、模板、导入 |
| 双人群定位撕裂 | 中 | 高 | 一套引擎两套皮；对外只讲一个叙事 |
| 数据丢失 / 无同步 | 中 | 极高 | 自动备份、导出、V2 加密同步 |
| 产品膨胀成「人生 OS」 | 高 | 中 | 不做清单；每个视图必须回答问题 |
| 命名侵权 | 未知 | 高 | 商标检索、备选名 |
| 图示虚荣，好看但无决策价值 | 中 | 中 | 每个视图绑定一个具体问题与验收 |

## 11. 待验证假设

| 编号 | 假设 | 验证方式 | 通过阈值（建议，待校准） |
|---|---|---|---|
| H1 | 用户愿意在完成时补一句话 | 埋点：带自定义消息的完成记录占比 | ≥30% |
| H2 | 回填能提升首周留存 | A/B：有回填引导 vs 无回填 | D7 留存 +10pp |
| H3 | 用户能读懂主线图 | 5 人可用性测试 | ≥4 人能说出自己的主线 |

| H5 | 人生树能让程序员在没有人生叙事需求时也留下来 | 观察：MVP 种子中人生模式的打开率与次月留存 | 人生模式周活 ≥30%，且不显著低于项目模式 |

> 以上为待验证假设，不是已验证结论；对外表述不得当作事实使用。
