# V1-01 放下、归档与重新开始（V1）

## 1. 背景与目标

MVP 只覆盖了「走完」和「建错」两种结局：收尾或删除。长期使用还需要第三种状态——这件事现在不做，但不想删、也不想它继续挤在今天；以及第四种整理动作——把已经结束的分支从默认树收起来，需要时再翻出来。

本 PRD 交付分支生命周期的后半段：放下（含原因）、重新开始、手动归档、取消归档，以及按一级分支浏览的归档区。

目标：用户能把一条不再推进的分支放下，今天页即刻清空它的待办；能在归档区找到并恢复一条已收起的分支；恢复后分支回到原来的位置与生命周期状态，额度与今天分组随之正确变化。

## 2. 范围与非目标

**范围**

- D-06 放下：必填原因；`status=dropped`；分支保留在默认树；未完成待办移出今天；历程用灰线与放下日期表达。
- 重新开始：已放下分支回到 `active`；待办按原 `dueDate` 与 `plannedDate` 回到分组；保留上次放下原因与时间。
- D-07 手动归档：仅已合并或已放下、且没有进行中后代的分支可归档；整棵子树退出默认树、额度与停滞计算，历史与统计保留。
- 取消归档：恢复原位置与原状态；校验祖先可见性与剩余额度。
- 归档区 S02（`/branches?view=archived`）：按一级分支浏览，定位历程或取消归档。
- 扩展 B01 行尾菜单与 P03 详情页头；落地 B08、B09、B11、B12。

**非目标**

- 不改收尾规则与收尾确认（M08）；本 PRD 只允许对「已合并」分支补做归档与取消归档。
- 不做批量放下、批量归档、批量取消归档。
- 不做归档区的搜索与排序（搜索归 V1-04，排序归 V1-08）。
- 不做分支删除（M08）、不恢复已删除分支。
- 不改表结构；归档不是 `status`，只用 `archivedAt`。

## 3. 用户故事与主流程

**故事 1｜放下一条暂时不做的线**

`/branches/:id` 更多菜单 →「放下」→ 面板说明「未完成待办会移出今天，历史仍可查看」→ 必填原因（如「这学期先不跑步了」）→ 确认 → 分支留在树中并标记已放下；今天页不再出现它名下的待办；全部待办的「已放下」分组出现这些待办；历程中该泳道变灰并标出放下日期。

**故事 2｜重新捡起一条放下的线**

在已放下分支详情或归档区点「重新开始」→ 系统检查祖先：祖先均可见且未合并 → 确认 → `status=active`，待办按原截止日期回到逾期 / 今天 / 未来 / 无截止；原先 `plannedDate = today` 的待办仍进今天组；页面显示「上次放下：11 月 3 日 · 这学期先不跑步了」。

**故事 3｜把结束的分支从树上收起来**

对一条已合并且没有进行中后代的分支 → 更多菜单「归档」→ 面板说明「会离开默认树、不再占用额度，历程仍可查看」→ 确认 → 分支从 `/branches` 消失，出现在归档区；全树额度减一；停滞计算不再包含它。

**故事 4｜在归档区找回一条旧分支**

`/branches?view=archived` → 按一级分支分组浏览 → 找到「2024 / 考研」→ 点「在历程查看」跳到该分支历史；或点「取消归档」→ 校验祖先可见与额度 → 确认 → 分支回到原位，状态仍为已合并或已放下。

**故事 5｜取消归档时祖先被归档**

在归档区对一条子分支点「取消归档」→ 若其父分支仍归档，操作不可用并提示「请先恢复上级分支」；恢复上级后，该子分支若曾单独归档，仍保持归档。

**异常与边界**

- 根分支不能放下、不能归档；菜单不提供对应动作。
- 放下原因为空或只有空白字符：保存不可用，输入保留。
- 已合并、已归档的分支不能放下；已合并分支只能归档，不能重新开始。
- 分支已有进行中的后代：不能归档，原因写明「还有进行中的子分支」。
- 分支已归档：放下、重新开始、再次归档均不可用；先取消归档。
- 重新开始时祖先已合并或已归档：不可直接重新开始；提示先移到可接收的位置，或先恢复祖先。
- 取消归档时父分支已满（L1 ≤7 / L2 ≤9 / L3 ≤20 或全树 >200）：不可用并显示剩余名额 0。
- 归档整棵子树时只写选中分支的 `archivedAt`；后代随祖先隐藏，不批量写归档标记，因此取消归档后未被单独归档的后代自动恢复可见。
- 写入失败：分支状态与 `archivedAt` 保持原值，页面提示失败并可重试；不出现「默认树已隐藏但归档区没有」的中间态。

## 4. 界面与交互

对应页面：**P02**（`/branches`）、**P03**（`/branches/:id`，状态与菜单）；视图：**B08、B09、B11、B12、S02**；入口扩展 **B01**。

### 4.1 放下（B08）

- 入口：P03「更多」与 P02 行尾菜单，动作名统一为「放下」；V1 起在 M08 的收尾、删除之后追加。
- 面板必含：一句「放下不是删除，分支会留在树上，历史仍可查看」；原因输入（必填）；「未完成待办会移出『今天』，可在全部待办的『已放下』里找到」。
- 确认按钮文案为「放下」；不可逆性只在数据层面表达为「可以重新开始」，不写「不可撤销」。
- 成功后 P03 页头显示 `已放下 · 11 月 3 日`，并在下方显示放下原因；操作区只保留「重新开始」与可用的结构动作。

### 4.2 重新开始（B12）

- 入口：已放下分支的 P03 与 P02 行尾菜单。
- 前置校验按顺序执行：分支未归档 → 祖先链上没有被归档的分支 → 祖先链上没有已合并分支；任一不满足则动作置灰并给出唯一原因。
- 祖先已合并时，面板提供「先移动到可接收的分支」入口（复用 B05 移动），移动成功后再开放重新开始。
- 确认后不弹二次确认；成功后回到 P03，页头恢复为进行中，展示「上次放下」信息。
- 待办分组即时刷新：逾期 / 今天 / 未来 / 无截止按原 `dueDate` 与 `plannedDate` 重新计算（R8、R15）。

### 4.3 手动归档（B09）

- 仅当 `status` 为 `merged` 或 `dropped`、且子树中没有 `active` 后代、且自身 `archivedAt` 为空时可用。
- 面板必含：分支路径；「离开默认树」；「不再计入分支额度」；「历程、提交、里程碑、统计仍然保留」；「可随时取消归档」。
- 已合并分支若在收尾时已归档，不重复提供归档；只提供取消归档。
- 确认按钮文案为「归档」，不使用「确定」。

### 4.4 归档区（S02）

- 路由 `/branches?view=archived`；从 P02 页头「归档」切换进入，返回恢复原视图与滚动位置。
- 按一级分支分组；组头显示该一级分支名与归档条数；行内显示分支路径、生命周期状态（已合并 / 已放下）、归档日期。
- 行内动作只有两个：在历程查看、取消归档。其余结构动作不可用。
- 祖先已归档的后代不出现在归档区顶层，随祖先一起展示为缩进行，避免同一子树重复列出。
- 归档区不提供新建、移动、重命名。

### 4.5 取消归档（B11）

- 入口：S02 行内、P03 已归档页头。
- 前置校验：祖先链上是否存在仍归档的分支；恢复后是否超出所在父的 L1/L2/L3 上限或全树 200。
- 面板必含：恢复后的路径、恢复后的状态（已合并 / 已放下）、将重新占用的额度。
- 确认后：清空该分支的 `archivedAt`；`status` 保持不变；回到默认树原位置。

### 4.6 五种状态

| 状态 | 表现 |
| --- | --- |
| 空 | 归档区无内容：一句「还没有归档的分支」+「回分支树」；树内不出现空的已放下分组 |
| 加载 | 保留归档区分组骨架与行高；计算子树进行中后代与额度时按钮不可用，不整屏 spinner |
| 错误 | 读取失败：保留外框，说明 + 重试；放下、归档、取消归档写入失败：状态不变，面板保留输入与选择并提示重试 |
| 只读 | 已归档子树只读（R14）；已合并分支只读；只允许取消归档与在历程查看 |
| 无权限或未登录 | 不适用；V1 无账号，所有生命周期操作不要求登录 |

### 4.7 移动端

- 390 px：放下、归档、取消归档、重新开始均为全屏面板，顶部标题与关闭；原因输入多行显示，键盘弹起时确认按钮保持可见。
- 归档区按一级分支折叠；行内动作收进行尾「更多」，不依赖悬停。
- 放下与归档的确认按钮点击区域不小于 44 px。

## 5. 数据与规则

| 表 | 字段 | 用途 |
| --- | --- | --- |
| `branches` | `_id`、`parentId`、`path`、`depth`、`status`、`archivedAt`、`droppedAt`、`dropReason`、`finishedAt`、`finishedIntoId`、`taskTotal`、`taskDone`、`commitCount`、`ownLastCommitAt` | 生命周期、归档可见性、额度、停滞 |
| `tasks` | `branchId`、`status`、`dueDate`、`plannedDate` | 放下后移出今天；重新开始后回到分组 |
| `commits` | `branchId`、`sourceBranchId`、`voidedAt` | 历史与统计保留，不因归档删除 |
| `milestones` | `branchId`、`achievedAt` | 归档后历史仍可查看 |
| `events` | `entityType='branch'`、`action='branch.pause'` / `'branch.resume'` / `'branch.archive'` / `'branch.unarchive'`、`payload`、`at` | 历次放下原因、恢复与归档留痕 |

规则：

- R15 放下：`status=dropped`，写 `droppedAt` 与 `dropReason`；未完成待办不改 `branchId`，只从今天分组排除；后代保留各自状态，进行中的后代照常出现在今天。
- R15 重新开始：`status=active`；按原 `dueDate` 与 `plannedDate` 回到 R8 分组，`plannedDate = today` 的仍先归今天组；**保留** `droppedAt` / `dropReason` 作为「上次放下」展示，不清空；历次记录在 `events`。
- R14 归档：只写 `archivedAt`，`status` 不变；归档子树退出默认树、快速添加候选、额度计算与停滞计算；历程、提交、里程碑与统计保留。
- R14 取消归档：只清 `archivedAt`，`status` 不变；恢复原位置；重新计入额度；祖先仍归档时不允许，单独归档过的后代保持归档。
- R16 额度：归档后释放名额；取消归档重新占用；校验 L1 ≤7、L2 ≤9、L3 ≤20、全树 ≤200，只算未归档、未删除的分支；根分支不计入全树 200。
- R8 今天三组：父分支 `dropped` 或归档的待办不进今天；重新开始后按原日期参与分组。
- R4 停滞：归档子树退出停滞计算；已放下分支不参与停滞判定，历程以灰线与放下日期表达。
- R7 四计数：放下、重新开始、归档、取消归档都不改 `taskTotal` / `taskDone` / `commitCount` / `ownLastCommitAt`；归档不重算统计。
- 根分支：`parentId=null`，不提供放下、归档、重新开始。
- 层级与路径：归档、取消归档均不改 `parentId`、`path`、`depth`、`order`、`pinnedAt`。

## 6. 验收标准

1. 对一条进行中分支执行放下，原因为空时确认按钮不可用；填写原因后成功，P03 页头显示已放下、放下日期与原因。
2. 放下后该分支的未完成待办不再出现在今天页任意一组；在 `/today/all` 的「已放下」分组可找到，且每条只出现一次。
3. 放下一条分支后，其进行中的子分支待办仍出现在今天页，状态不受影响。
4. 历程中该分支显示为灰色泳道，并标出放下日期；该分支的既有提交、里程碑仍可打开。
5. 对已放下分支点「重新开始」，成功后退回进行中；`plannedDate = today` 的待办进今天组，其余按 `dueDate` 分别进入逾期、今天、未来或无截止。
6. 重新开始后 `droppedAt` 与 `dropReason` 仍可查看，页面显示「上次放下」；`events` 中新增 `branch.resume`。
7. 根分支的菜单不出现放下、归档、重新开始；已合并分支不出现放下与重新开始。
8. 对一条含进行中后代的分支点「归档」，动作不可用并写明「还有进行中的子分支」。
9. 对已合并且无进行中后代的分支归档成功：它从 `/branches` 消失，出现在 `/branches?view=archived`，全树额度减一，停滞列表不再包含它。
10. 归档区按一级分支分组；行内只有「在历程查看」与「取消归档」；记录显示生命周期状态与归档日期。
11. 取消归档成功后分支回到原父分支原顺序，`status` 与归档前一致；全树额度加一。
12. 父分支仍归档时取消归档子分支不可用并提示先恢复上级；恢复上级后，曾单独归档的子分支仍留在归档区。
13. 取消归档会使所在父的分支数超过 7 / 9 / 20 或全树超过 200 时，操作不可用并显示剩余名额 0。
14. 人为使写入失败：分支状态与归档可见性均不变，界面提示可重试；不出现归档区与默认树同时缺失该分支。
15. 390 px 下四种操作均为可关闭的全屏面板，放下原因可完整输入，确认按钮在键盘弹起时可见。

## 7. 依赖与阶段、未决问题

- 阶段：V1。
- 依赖：M02（树、菜单、额度）、M04（详情页头与更多菜单）、M08（收尾与已合并状态）。
- 后续消费：M03 全部待办的「已放下」分组、M06 历程灰线与归档历史、V1-02 年轮统计、V1-05 断舍离徽章、V1-08 排序与置顶。
- 与既有文档的关系：
  - M08 写明「MVP 收尾归档后无界面恢复入口」；本 PRD 的取消归档补上该入口，不改变 M08 的收尾规则。
  - M08 留下的「留在树上的已合并分支能否再归档」在本 PRD 定为：可以，条件同 D-07。
  - M03 写明「已放下分组在 D-06 上线前为空组」；本 PRD 交付后该分组有内容，M03 的分组规则不变。
- 冲突与处理：
  - `FRAMEWORK` 「放下」的表述曾写「未完成待办停留在原分支」，与 D-06「未完成待办退出今天」是同一件事的两面：待办不迁移 `branchId`，只退出今天分组；本 PRD 按后者写，并在详情与全部待办中保留可查看、可改归属。
- 未决问题：
  - 已放下分支是否允许改名、改色、移动：本 PRD 按「未归档的已放下分支可移动（沿用 §2.6）」处理，改名与改色未单独开放，需产品确认。
  - 归档区是否需要显示归档前的提交数与最后活动日期，取决于画稿行内空间，当前按「路径 + 状态 + 归档日期」实现。
  - 取消归档后是否需要在历程中新增一条「恢复」标记，当前只在 `events` 留痕，不改历程视觉。

**最值钱的回归用例**：`branch-visibility.test.ts` 里的「归档只写选中分支、取消归档后后代自动恢复可见」守的是递归给整棵子树写 `archivedAt` 这一类 bug——取消归档只清选中行，后代永久隐藏，默认树与归档区同时都看不到它。手工点页面时只有在「祖先归档 + 其中一层曾单独归档」的多层结构下才会暴露，扁平数据下完全看不出来。其次是 `branch-quota.test.ts` 里的「额度只算未归档、未删除分支」：守的是归档后仍占名额，用户明明归档了却无法新建，只有精确造到 7 / 9 / 20 / 200 边界才会看到「剩余名额 0」。

说明：动作可用性、额度与可见性都能用纯函数断言，已进单测；写入与事件留痕走 `fake-indexeddb`；面板、泳道灰线与滚动恢复留在 8.3。

### 8.3 只能人工验收

1. **放下原因输入与键盘**：前置 一条进行中分支；操作 390 px 打开放下面板，输入多行原因后删空再输入；判定 多行可完整输入、留空时确认置灰且输入保留、键盘弹起时确认按钮可见。为什么不能进单测：真实键盘、焦点与输入法行为无法在单测中复现。

3. **归档区返回与滚动位置**：前置 默认树可滚动；操作 从 P02 进入 `/branches?view=archived` 再返回；判定 恢复原视图与滚动位置，筛选不丢失。为什么不能进单测：路由状态与滚动恢复依赖浏览器。
4. **390 归档区折叠与行尾「更多」**：前置 至少两条一级分支各有归档；操作 390 px 折叠一组并展开行尾菜单；判定 按一级分支折叠、动作收在「更多」且不依赖悬停、确认按钮点击区域不小于 44 px。为什么不能进单测：触控尺寸与悬停行为是设备行为。
5. **写入失败不出现中间态**：前置 一条可归档分支；操作 在 DevTools 中使 IndexedDB 写入失败后执行归档；判定 面板保留选择并提示重试，分支既不从默认树消失、也不在归档区缺失。为什么不能进单测：需真实浏览器制造写入失败；回滚本身由 8.2 覆盖。
